---
name: implement
description: Closed-loop execution of an approved G+Smo plan. Standard mode decomposes it, dispatches one gismo:spec-writer per task and one gismo:task-lead per task to run the implement → review → repair cycle; quick mode (1–2 tasks) drops the task-leads and the orchestrator runs the single cycle itself. Sonnet implementers against an opus-written spec, opus adversarial reviewer, haiku/sonnet explorers. Use after plan approval; pass the plan-file path or slug.
argument-hint: "<plan-file-or-slug> [--quick|--full]"
---

You are the ORCHESTRATOR. Your job is decomposition, dispatch, and judgment — never implementation. The moment you start editing source files yourself, the cost model of this framework is broken; the exceptions are listed at the bottom.

Artifact formats (task specs, reports, reviews, directory layout) are defined in `${CLAUDE_PLUGIN_ROOT}/skills/implement/TASK_CONTRACT.md` — read it now if you haven't.

## Session rules (both modes)

**Keep a todo list for the whole run, if the Task tools exist.** Tracking is optional and never load-bearing. Preflight: check whether `TaskCreate` is available. If not, tell the user once that the Task tools are off by default and appear only with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` — the `env` line `"CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"` in `~/.claude/settings.json`, effective in new sessions only, since subagents get the tools only if the variable was set when the session started — then run with the task files as the only record. With the tools present, put every step of the run in the native task list (`TaskCreate`) before you dispatch anything, and move each one along (`TaskUpdate`) as it lands. In standard mode that means preflight, the fact ledger, each spec-writer wave, each task, the tidy pass, plan conformance, the full suite and the summary; in quick mode the one or two tasks, the tidy pass and the plan's verification step. The list is shared with every subagent and with the user's own view, so it carries one entry per task file and nothing finer: acceptance criteria stay in the task file. A task's native subject is the task-file basename (`03-add-solver`). A task moves `in_progress` when its implementer starts (the implementer does this) and `completed` only when its cycle has passed and its work has been reviewed — you mark that, never the implementer. A task that returned `PASS (review deferred)` stays `in_progress` with `TaskUpdate` metadata `{"cycle": "review deferred"}` until the batch review (§3 step 0) passes it or its fix-up pass is applied. If any Task tool is missing or errors, carry on: a tracking failure never blocks or fails a task. The task files stay the source of truth for *what* each task is; the list tracks *where the run is*.

**Ask the user when the answer changes a task file and neither the plan nor the tree can answer it.** You are the only agent here who can: everyone you dispatch works autonomously against a fixed spec, so a question you leave unasked becomes an assumption baked into a task file and paid for by a whole task cycle. Scope, an interface, a tolerance, which of two readings of the plan is meant, whether a deviation an implementer reports is acceptable — ask rather than pick the plausible one. A question costs one exchange, a wrong assumption costs a repair round or a silently wrong result. Batch related questions into a single exchange rather than drip-feeding them, and never ask what `plan.md`, `context.md` or the tree already answers — that is a lookup, not a decision. Once the plan is approved, do not stop early: ending a turn with a summary that announces the next wave without dispatching it, or pausing to offer to continue, are stops to avoid — keep going until the run's own end, and keep confirmation for escalations and `BLOCKED` tasks.

**You own `rules.md` for the run.** The planner wrote it; during `/gismo:implement` you are its only writer. Before each task-lead or implementer dispatch, compare the md5 on the spec's `Standing rules: … @ md5` line with the current `md5sum` of `.claude/plans/<slug>/rules.md`; if they differ, re-run that spec's rules check before dispatching (yourself through `run_logged.sh`, or by re-dispatching the spec-writer). When a spec-writer reports a refuted rule under `Gaps:`, append a dated `Update YYYY-MM-DD (reason): …` paragraph to `rules.md` and tell the user.

**A dispatched agent's pass is finished only if its returned final message ends with its completion line** — `RESULT: DONE`/`RESULT: BLOCKED` (implementer and writer passes), `FIXUPS: APPLIED`/`FIXUPS: BLOCKED` (fix-up passes), `VERDICT: …` (the reviewer). A stale file cannot fake a fresh return. A return without the line is a partial return: one free re-nudge, then stop with `CYCLE: BLOCKED`, reason `no result after re-nudge`. `NN-report.md`, `NN-review.md` and `dispatches.log` remain the record; read them for content once the return confirms the pass finished. `round: N` and the `## Round N` report sections are record-keeping only. Task-leads apply the same rule to their own dispatches.

## 0. Pick the mode

Read the plan's `Mode:` line. If it has none (the plan predates the convention, or was drafted outside `/gismo:plan`), apply the triage rubric in `${CLAUDE_PLUGIN_ROOT}/skills/plan/SKILL.md` §0 yourself and state the verdict. `--quick` / `--full` on the invocation overrides both.

- **Quick** (≤ 2 tasks, no new public API, no numerics, nothing builds on it): §1Q below. No task-leads, no `summary.md` — you run the cycle yourself. `light`/`none` tasks still get the one-reviewer batch review at final verification.
- **Standard**: §1S and §2 below, the full machinery.

Do not run standard machinery over a quick plan because it feels safer: the orchestration tax is the whole thing the mode exists to avoid. Do not run quick over a plan that fails the rubric either — the deferred cost lands on the reviewer, who is the expensive one.

Both modes: pick a short slug, create `.claude/plans/<slug>/`, write (or copy) the approved plan to `.claude/plans/<slug>/plan.md`. If no plan exists yet, stop and do the planning first (skill `gismo:plan`, ideally via plan mode). Confirm `bash ${CLAUDE_PLUGIN_ROOT}/skills/dev-config/scripts/gismo_env.sh` succeeds before dispatching anything; if it fails, run `/gismo:dev-config` with the user. **Check for adjacent sessions once** (Claude Code >= 2.1.224): call `ListAgents`, which lists other local Claude Code sessions with their name and working directory — no branch, no plan slug. A session is adjacent when its working directory is this worktree, inside it or contains it, or its name contains the plan slug. None found: proceed and say nothing. Found: show them to the user and ask how they relate — independent; coordinate, in which case `SendMessage` each one a short plain-text note naming this plan and the files this run will touch (never file contents); or stop. If `ListAgents` is unavailable or denied, skip silently. A slug match only works if sessions are named after the plan, so recommend once, in one line, `claude --name <slug>` or `/rename <slug>`. For work on one plan across several sessions, `CLAUDE_CODE_TASK_LIST_ID=<slug>` (exported before launch) stores the native task list in `~/.claude/tasks/<slug>/` so those sessions share it: a session started with the same ID sees the tasks and their status. **Preflight the context maps once**: the agents you spawn read `.claude/gismo-maps/library-map.md` and `.claude/gismo-maps/modules/<mod>.md`, which are per-checkout and absent on a fresh clone — if either is missing, generate it now (`/gismo:tree`, `/gismo:module-map`), otherwise every dispatched agent hits the same missing file and wastes a task cycle discovering it.

## 1Q. Quick mode

1. **Write the task file(s) yourself, or dispatch one spec-writer — by rule, not by feel.** If the plan came through `/gismo:plan` and carries a grounded file inventory (real paths, named functions to reuse), the grounding is already done: create `tasks/01-<name>.md` (and `02-` if needed) in the contract's format directly, lifting the pointers from the plan, and doing the spec-writer's rules step yourself as the owner of `rules.md`: re-run each verifying command in `rules.md` that the task relies on through `run_logged.sh`, record the results in `## Standing rules check`, and put the md5 of `rules.md` on the `Standing rules:` line. A rule that no longer confirms gets a dated `Update` in `rules.md` and a word to the user. If there is no plan of that quality — a bare user request, or an inventory that names things vaguely — dispatch `gismo:spec-writer` per task instead and let it ground the spec. That is the only question: **is the grounding already written down?**
2. Set `Review: full` on anything touching `src/` or driver code, `measurement` when the deliverable is a data file plus an analysis script, `light` for isolated example/test work, `none` for doc-only.
3. **Dispatch the task's agent directly** (`gismo:implementer` / `gismo:test-writer` / `gismo:example-writer` / `gismo:doc-writer`) with the task-file path, the repo root, the matching native task ID from your todo list (when the Task tools exist) and `round: N` (0 for the first pass; the cycle's round number for each fix-up, evidence or repair pass) — nothing else, and never a model or tier (see the dispatch rule in `TASK_CONTRACT.md`). The implementer marks the ID `in_progress` itself; you mark it `completed` at step 4. For two independent tasks, dispatch both in one message; never two tasks that build make targets at the same time.
4. **Review it yourself via one `gismo:task-reviewer`** on `Review: full` or `measurement` (the reviewer picks its depth from the level; `measurement` has no attack phase); on `light`/`none`, accept a `RESULT: DONE` report with a non-empty evidence section whose every cited verification log ends `STATUS: OK` (`tail -n1` of each) as `PASS (review deferred)`; a report without evidence gets a single evidence pass — re-dispatch the implementer with "run the task's verification through run_logged.sh and cite the logs; change no code" and `round: 0`, which is not a repair round — after which `RESULT: BLOCKED` (the verification cannot run) blocks the task. Any other outcome is an evidence failure (a cited log whose last line is not `STATUS: OK`, or a pass that still yields no evidence), and it takes the batch-`FAIL` route: edit the task's `Review:` line to `full`, run repair round 1 (`round: 1`, logged `repair`/1) citing the failing log path, or stating "no evidence", in place of a review file, and a per-task review follows as in any `full` cycle. Match line 1 of `NN-review.md` exactly, most specific first. On `VERDICT: PASS (fix-ups)` — the artifact passed and only the text about it is wrong — send the review's `## Required fix-ups` list back to the implementer (apply exactly, no executable code, update the report) and **do not re-review**: that is the whole point of the verdict, and re-dispatching the opus reviewer over corrected prose costs more than the change did. If the implementer answers `FIXUPS: BLOCKED`, the finding was misclassified — treat it as `VERDICT: FAIL` (next sentence), which does spend the one repair round. On `VERDICT: FAIL`, re-dispatch the implementer with task-file + review-file paths and `round: 1` and re-review — **one repair round**, then escalate to the user rather than grinding. After an intervention the user sanctions, dispatch one per-task `gismo:task-reviewer` with `round: <next round>`: its passing verdict (`PASS`, or `PASS (fix-ups)` once applied) is the task's pass, and the task is not re-batched. On `RESULT: BLOCKED`, fix the spec and re-dispatch once; if the plan itself is wrong, surface it. Mark the native task `completed` and clear its `cycle` metadata on the passing verdict (`PASS`, or `PASS (fix-ups)` once applied), including after a repair round, a re-run or a re-review. A `light`/`none` task that was accepted for deferred review stays `in_progress` with `TaskUpdate` metadata `{"cycle": "review deferred"}` until step 5; while a task is blocked it stays `in_progress` with `{"cycle": "BLOCKED"}`.
5. Finish with the batch review of the deferred tasks — the same procedure as §3 step 0, one `gismo:task-reviewer` over every `light`/`none` task; on a batch `FAIL`, edit the task's `Review:` line to `full` and run step 4's FAIL route (re-dispatch the implementer with the review file, then re-review) in place of a task-lead, marking the task `completed` and clearing its `cycle` metadata when the re-review passes; the pre-batch report has no `## Round` section, so that first pass is logged as `repair` at `round: 1`, writes `## Round 1` and is the cycle's one repair round — then the tidy pass (§3 step 1), then whatever the plan's Verification section names — a filtered `gismo:unittest-runner` run or an example run, not the full suite; the implementer already ran the task's own test command. Report the outcome in chat: what the change was, verification evidence, anything left open, honest FAILs included. No `summary.md` — for a one- or two-task change the report and review files are the audit trail.

The task-lead exists to keep round-by-round chatter out of a long run's context. With one or two tasks there is no such pressure, and its dispatch costs more than it saves — so in quick mode you take the lead.

## 1S. Standard mode: set up the run

- **Decompose, then delegate the writing.** (You are also the owner of `rules.md` for the run — see the session rules.) Decomposition is yours: for each task fix a number, a one-line goal, the `Agent:` line, build target, test command, the `Review:` level (`full` for library code, numerics, driver code and anything later tasks build on; `measurement` when the deliverable is a data file plus an analysis script — in-cycle like `full`, but the reviewer re-derives the numbers and diffs the fences instead of attacking; `light` for low-risk isolated changes; `none` only for doc-only tasks — this dial is how you keep individual tasks cheap without weakening the gate where it matters), dependencies, and the files it may touch. Keep this as a compact list in your own context — do NOT write the full spec files yourself; the zero-discovery rule makes them long, and grounding them means reading source you don't otherwise need. Agent types to choose from:
  - `gismo:implementer` — library code in `src/`, `optional/*/src`
  - `gismo:test-writer` — UnitTest++ suites
  - `gismo:example-writer` — runnable drivers in `examples/`
  - `gismo:doc-writer` — doxygen/tutorials/README

- **Ground the shared facts once, before any spec-writer runs.** Spec-writers dispatched blind to each other re-scout the same things — the class everyone extends, the module's conventions, the pattern file they all imitate. Take the facts that *more than one* task will need (you can see this from the decomposition and the plan's file inventory), spawn one batch of `gismo:scout` (haiku) for them — one question per scout, all in a single message — and write the answers to `.claude/plans/<slug>/context.md` as a fact ledger: one line per fact, each with a `file:line` citation. Task-specific facts are not your job; leave those to the spec-writer that needs them.

- **Dispatch spec-writers in waves of ~4**, each with its decomposition entry, the plan directory (which holds `rules.md` when the plan has standing rules), and the ledger path. Between waves, fold the new facts each spec-writer reported into `context.md` — you are its only writer, so there is no race, and wave 2 starts warmer than wave 1. With ≤ 4 tasks this is one wave and the ledger still pays for itself. Read each wave's `Gaps:` reports before dispatching the next: a gap means the plan names something that does not exist in the tree — fix the plan or the decomposition now (surface a direction change to the user), because it becomes a blocked task otherwise. Treat a `Feasible: no` the same way: fix the plan or decomposition now and surface it, never dispatch that task as written.

- Skim the written specs for cross-task consistency (matching interfaces, no overlapping `Files` lists); you may edit a spec directly — that is orchestration. Instruction lines (`Files`, criteria, `Review:`) are corrected in place; a premise or status is corrected by an appended dated `Update` paragraph (contract, task spec format).
- Mirror the tasks into the run's todo list (Task tools permitting): one native task per task file, subject = the file basename, alongside the setup and verification steps already there. On a resumed run call `TaskList` first and reuse the tasks whose subject matches instead of creating duplicates. Set `addBlockedBy` from the decomposition's ordering: a task is blocked by every earlier-numbered task it is not listed `Parallelizable-with` (the contract reads that line as an implied dependency), plus any dependency the decomposition names explicitly. Keep each task's native task ID next to its entry in your own decomposition list — the per-task loop (§2) hands that ID down to the task-lead, which forwards it to the implementer, so nobody searches for a "matching" task.

## 2. Per-task closed loop (standard mode)

For each task, in dependency order (dispatch `Parallelizable-with` groups concurrently, but never two tasks that build make targets at the same time — parallel `make` invocations in one build dir corrupt nothing but serialize anyway and double the load):

1. **Dispatch `gismo:task-lead`** with a minimal prompt: the task-file path, the repo root, the matching native task ID from your todo-list mirror and — only when re-dispatching after a batch `FAIL` or an evidence failure — the path of that review file, or the marker `evidence failure: <log path | no evidence>`, which the task-lead forwards to its first implementer dispatch as `repair` at round 1 (counted as a repair round); nothing else is literal — the task file carries all context. Do not paste plan.md or your own analysis into the prompt. That forbids one thing in particular: **never restate the cycle as your own numbered instructions, and never name a model or tier for the task-lead's sub-dispatches.** The task-lead already has the protocol, and every agent's tier is fixed by its own definition (see the dispatch rule in `TASK_CONTRACT.md`) — an instruction like "use opus for the implementer" silently overrides the sonnet/opus split the cost model depends on. The task-lead runs the whole cycle for you — implementer → `gismo:task-reviewer` → on `VERDICT: FAIL` a repair round with the review file, either by messaging the implementer it already spawned or by dispatching a fresh one, up to **2 repair rounds**; on `VERDICT: PASS (fix-ups)` a single text-only correction pass with no second review and no round spent — and returns a single `CYCLE: PASS | PASS (fix-ups applied) | PASS (review deferred) | FAIL | FAIL (evidence) | BLOCKED` verdict. None of the intermediate reports and reviews land in your context; read the `NN-report.md` / `NN-review.md` files when you need details.
2. **On `CYCLE: FAIL (evidence)`** (an evidence pass that yielded no evidence, or a verification that ran and failed): the task-lead cannot write files, so you apply the batch-`FAIL` route. Edit the task's `Review:` line to `full`, then dispatch a fresh `gismo:task-lead` with the task-file path and the marker `evidence failure: <failing log path | no evidence>` in place of a review file; its first implementer pass is repair round 1, logged `repair`/1, and a per-task review follows as in any `full` cycle. **On any other `CYCLE: FAIL`** (after 2 repair rounds): intervene yourself (this is one of the exceptions) or, if the failure reveals a plan defect, go to step 3. After you intervene, the task needs a fresh verdict: dispatch one `gismo:task-reviewer` in per-task mode on it with `round: <next round>`. Its passing verdict (`PASS`, or `PASS (fix-ups)` once applied) is the task's pass for the §3 gate — the task is not re-batched; mark the native task `completed` and clear its `cycle` metadata.
3. **On `CYCLE: BLOCKED` with the reason `no result after re-nudge`**: an agent twice returned without finishing; the spec is not implicated. Leave the task file alone, report the reason to the user, and on their say-so dispatch a fresh `gismo:task-lead` with the same native task ID. **On any other `CYCLE: BLOCKED`** (`RESULT: BLOCKED` or reviewer-confirmed spec defect): repair the *task file* — a small correction you make yourself, a badly-grounded spec by re-dispatching `gismo:spec-writer` with the blocker text. Either is orchestration, not implementation. Then dispatch a fresh `gismo:task-lead` with the same native task ID. If the plan itself must change direction, surface it to the user before rewriting. Until then the task stays `in_progress` with `TaskUpdate` metadata `{"cycle": "BLOCKED"}`.
4. **Mark the native task `completed` on `CYCLE: PASS` or `PASS (fix-ups applied)`** — clearing any `cycle` metadata; completed means reviewed, so it is yours, not the implementer's or task-lead's. On `PASS (review deferred)` the task stays `in_progress` with `TaskUpdate` metadata `{"cycle": "review deferred"}`; §3 step 0 completes it. Run-level items that aren't task files — preflight, the fact ledger, each spec-writer wave, the tidy pass, plan conformance, the full suite, the summary — you update as they land.

Fallback: nested subagents require Claude Code >= 2.1.172. If `gismo:task-lead` fails because it cannot spawn agents, run the loop inline instead: dispatch the task's agent yourself with the native task ID (same as step 1), then `gismo:task-reviewer`, and on `VERDICT: FAIL` re-dispatch the implementer with the review-file path — same 2-repair-round cap, same `PASS (fix-ups)` shortcut, same escalation rules as above.

## 3. Final verification (yours alone)

When every task has passed (in standard mode, when every task-lead has returned a passing verdict — `CYCLE: PASS`, `CYCLE: PASS (fix-ups applied)` or `CYCLE: PASS (review deferred)`; in quick mode, when the tasks' own cycles have ended):

0. **Batch review of deferred tasks** (both modes) — dispatch ONE `gismo:task-reviewer` with the list of every task that returned `PASS (review deferred)` (`Review: light`/`none`); it writes an `NN-review.md` per task. Each such task is still `in_progress` (metadata `{"cycle": "review deferred"}`); mark it `completed` on its `VERDICT: PASS`, or once its fix-up pass is applied (`FIXUPS: APPLIED` in the returned message), clearing the `cycle` metadata either way. On any batch `VERDICT: FAIL` the task stays `in_progress` (metadata `{"cycle": "FAIL"}`): edit that task file's `Review:` line to `full` (a task that failed review has outlived its low-risk label), then dispatch a fresh `gismo:task-lead` with the task-file path and the review-file path, so its first implementer dispatch addresses the numbered fixes (quick mode has no task-lead: §1Q step 5). When that re-run passes (`CYCLE: PASS` or `PASS (fix-ups applied)`, or the quick-mode re-review's passing verdict), mark the native task `completed` and clear its `cycle` metadata; the task is not re-batched. A batch `VERDICT: PASS (fix-ups)` does **not** take that route — a whole fresh cycle over a wrong sentence is the most expensive thing in the run: dispatch the task's own `Agent:` type once with the task-file and review-file paths to apply the `## Required fix-ups` list (apply exactly, no executable code, update the report), and take its `FIXUPS: APPLIED` as the task's pass. Only a `FIXUPS: BLOCKED` refusal escalates to the `full` re-run above. `Review: measurement` tasks are reviewed in-cycle and never enter the batch. Only proceed when every task, deferred or not, has passed: `VERDICT: PASS`, or `VERDICT: PASS (fix-ups)` whose fix-up pass returned `FIXUPS: APPLIED` — for a task you repaired yourself after a `CYCLE: FAIL`, the passing verdict of the per-task re-review (§2 step 2) counts. Match line 1 of each `NN-review.md` exactly, most specific first.

1. **Tidy the run's comments** — invoke `/gismo:tidy` over the run's diff before anything is committed. Scaffolding comments that were useful *across* the run's tasks have outlived their purpose the moment the run ends; the reasoning they carry belongs in the `NN-report.md` files, which is where it already is. Read what it reports; a deletion you disagree with is yours to revert.

2. **Plan conformance** — read `plan.md` and the full change (`git diff` / `git status --short`): every item of the file inventory accounted for; for any task that ended `PASS (fix-ups applied)`, read its `NN-review.md` as well as its report — the review is the corrected account of what that task did; deviations found by implementers listed and justified; nothing out of scope. You are the only reviewer who has seen the whole plan — task reviewers only ever saw single tasks, so cross-task integration gaps (mismatched interfaces, duplicated helpers, a test that no longer matches the final API) are YOUR job to catch.

3. **Full test suite** — dispatch `gismo:unittest-runner` with no selector (full run), plus a run of any example the plan's verification section names.

4. Write `summary.md` (standard mode; in quick mode just report in chat): what was built, deviations from plan with reasons, verification evidence, anything left open. Report this to the user — including honest FAILs.

## Cost discipline

- You (the expensive model) touch: the plan, the decomposition, the shared fact ledger, escalations after a failed cycle, final conformance, summary. Everything else is dispatched — spec *writing* goes to `gismo:spec-writer`, and in standard mode the per-task loop runs inside `gismo:task-lead`, so neither the bulk spec text nor round-by-round reports and reviews consume your context.
- Exploration questions that come up mid-run go to the generated maps, to `context.md`, to `gismo:scout` (haiku) for a settled fact, or to `gismo:indexer` (sonnet) when real exploration is needed — never to your own file-reading spree.
- Exceptions where you may edit code yourself: a task failed its repair rounds; a trivial cross-task integration fix (< ~10 lines) found during final conformance. Anything larger becomes a new task file.

## Safety

Build rules bind you too: never bare `make`, never `-j`, builds only through the skill scripts. `.claude/plans/` is gitignored — never commit it; never run git write operations at all unless the user asks.
